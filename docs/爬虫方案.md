# CraftifyX Miner 6.0 -- 爬虫方案选型

> **版本**：v1.0（2026-03-22）  
> **结论**：初版使用 Apify 托管采集，后续遇瓶颈再引入 Scrapling 自建补充

---

## 一、采集需求概览

| 采集环节 | 数据内容 | 日处理量 | 反爬难度 | 代理要求 |
|----------|---------|---------|---------|---------|
| L1 浅层扫描 | Following 列表（UserID + Bio） | ~5,000 人 | 中 | Datacenter（低成本） |
| L3 深度抓取 | Profile 完整信息 + 最近 10 条 Tweets | 300-500 人 | 高 | Residential（高可用） |
| 未来：创作者主页 | 个人网站 / Gumroad / Patreon | 按需 | 低-中 | 视站点而定 |
| 未来：多平台扩展 | Pixiv / DeviantArt / ArtStation | 按需 | 中 | 视站点而定 |

目标平台：**Twitter/X 为主**（初版），后续扩展到创作者聚集的其他平台。

## 二、候选方案

### 方案 A：Apify 托管采集（当前选择）

[Apify](https://apify.com/) 是一个云端 Web Scraping 平台，提供现成的 Actor（爬虫脚本市场）、托管代理池、Webhook 回调等能力。

**工作方式**：
```
代码触发 Apify Actor run → Apify 云端执行爬取 → 完成后 Webhook 通知我方服务器 → 拉取数据入库
```

**优势**：
- Twitter/X 专用 Actor 成熟稳定（`apidojo/twitter-scraper-v2` 等），开箱即用
- 零运维：爬虫在 Apify 云端运行，不占我方服务器资源
- 代理内置：Datacenter / Residential 代理通过配置切换，无需自行采购
- Webhook 集成：Actor 完成后自动回调，与我方 Flask 管道无缝衔接
- 社区生态：Actor 市场有大量第三方维护的 Twitter Scraper

**劣势**：
- 第三方依赖：Actor 可能下架、涨价、API 变更
- 定制性有限：无法深度自定义抓取逻辑（如条件中断、动态调整抓取深度）
- 平台扩展性：非 Twitter 平台可能找不到合适 Actor，需自己写
- 费用结构：$49/月订阅 + 代理流量约 $330/月，其中代理流量是大头

**月度费用**：
| 项目 | 费用 |
|------|------|
| Starter 订阅 | $49 |
| Datacenter 代理 (L1, ~300GB) | ~$90 |
| Residential 代理 (L3, ~20GB) | ~$240 |
| **合计** | **~$379** |

### 方案 B：Scrapling 自建爬虫

[Scrapling](https://github.com/D4Vinci/Scrapling)（31.8k GitHub stars）是一个 Python 自适应 Web Scraping 框架，从单次请求到大规模爬取全覆盖。

**核心能力**：
| 能力 | 说明 |
|------|------|
| StealthyFetcher | 绕过 Cloudflare Turnstile 等反爬，指纹伪装 |
| Adaptive 选择器 | 网站结构变化后自动重定位目标元素 |
| Spider 框架 | Scrapy 风格 API，并发爬取 + 暂停/恢复 |
| ProxyRotator | 内置代理轮换，支持自定义策略 |
| 多会话支持 | 同一 Spider 中混合 HTTP 请求和隐身浏览器 |
| MCP Server | AI 辅助抓取（可与 Claude/Cursor 集成） |

**优势**：
- 完全自主可控，不依赖第三方平台
- 抓取逻辑完全可定制（条件中断、动态深度、自定义解析）
- 跨平台扩展方便（写新 Spider 即可抓 Pixiv/DeviantArt 等）
- Adaptive 选择器应对网站结构变化
- 无订阅费，仅需自购代理

**劣势**：
- Twitter/X 反爬极其激进：自己写 Twitter Spider 工程量大、维护成本高
- 服务器资源要求高：跑 headless 浏览器并发需 4G+ 内存，当前 2C4G 轻量服务器可能不够
- 代理需自购：Residential 代理价格与 Apify 相当，不省费用
- 开发周期长：自建 Twitter 爬虫 + 反爬对抗至少增加 2-3 周

**月度费用**（假设自购代理）：
| 项目 | 费用 |
|------|------|
| 软件订阅 | $0（开源） |
| 代理服务商（如 Evomi / BirdProxies） | ~$300-400 |
| 服务器升级（4C8G 以跑浏览器） | +$5-10 |
| **合计** | **~$310-410** |

费用与 Apify 方案接近，但开发和维护成本更高。

## 三、关键对比

| 维度 | Apify（方案 A） | Scrapling（方案 B） |
|------|----------------|-------------------|
| Twitter/X 专项能力 | 成熟 Actor，开箱即用 | 需自写 Spider + 对抗反爬 |
| 开发周期 | 即插即用（1-2 天调通） | +2-3 周（Twitter Spider 开发） |
| 运维负担 | 零（云端运行） | 需维护浏览器环境 + 反爬迭代 |
| 服务器资源 | 不占（云端） | 需 headless 浏览器（内存密集） |
| 费用 | ~$379/月 | ~$310-410/月（代理费依然要付） |
| 定制性 | 受限于 Actor 参数 | 完全可定制 |
| 平台扩展 | 依赖 Actor 市场 | 写新 Spider 即可 |
| 稳定性风险 | Actor 下架/涨价 | Twitter 反爬迭代需跟进 |
| 4 周内可交付 | 可以 | 有风险 |

## 四、决策

### 初版 (v1.0)：Apify 为主

- 使用 Apify 托管 Actor 完成 Twitter/X 数据采集
- 理由：
  1. 4 周交付时间紧张，Apify 开箱即用不增加开发风险
  2. Twitter 反爬复杂度高，自建 Spider 的 ROI 不划算
  3. 2C4G 轻量服务器无法承载 headless 浏览器并发
  4. 代理费用是大头（~$330/月），换自建方案省不了多少

### v1.1 可引入 Scrapling 做补充

引入时机：遇到以下任一瓶颈时考虑

| 瓶颈场景 | Scrapling 解决方式 |
|----------|------------------|
| Apify Actor 下架或涨价 | 用 Scrapling Spider 替代 Apify Actor |
| 需要抓取创作者个人网站 | StealthyFetcher 抓 Gumroad/Patreon 页面，补充 Monetization 指标 |
| 扩展到非 Twitter 平台 | 写 Scrapling Spider 抓 Pixiv/DeviantArt/ArtStation |
| 需要更精细的抓取控制 | 条件中断、动态调整深度、自定义解析逻辑 |

引入方式：**Apify 为主 + Scrapling 为备**的双轨采集架构

```
                    ┌── Apify Actor (Twitter/X 主力)
Seed 列表 → 调度器 ─┤
                    └── Scrapling Spider (补充采集 / 备用通道)
```

### v1.2 长期演进

- 用 Scrapling 的 Adaptive 选择器处理创作者主页的多样化结构
- 利用 MCP Server 与 AI 结合做智能数据提取
- 逐步降低 Apify 依赖比例，实现采集自主可控

## 附录：Scrapling 快速上手参考

安装：
```bash
pip install "scrapling[fetchers]"
scrapling install  # 安装浏览器依赖
```

基本用法（隐身抓取）：
```python
from scrapling.fetchers import StealthyFetcher

page = StealthyFetcher.fetch('https://example.com', headless=True)
data = page.css('.target-class::text').getall()
```

Spider 框架（并发爬取）：
```python
from scrapling.spiders import Spider, Response

class CreatorSpider(Spider):
    name = "creator_sites"
    start_urls = ["https://gumroad.com/creator1", "https://patreon.com/creator2"]
    concurrent_requests = 5

    async def parse(self, response: Response):
        yield {
            "url": response.url,
            "has_shop": bool(response.css('.shop-link')),
            "product_count": len(response.css('.product-card')),
        }

result = CreatorSpider().start()
```

更多文档：https://scrapling.readthedocs.io/
